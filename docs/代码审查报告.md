### BUG-1 [严重] 隐私锁 PIN 完全无法启用

**位置**：`src/stores/privacy.ts:47`、`src/stores/privacy.ts:61`

```ts
const record = ref<PrivacyRecord>({ enabled: false, salt: '', hash: '' })  // :16
// :45-47  setPin()
record.value = { enabled: true, salt, hash }
await kvSet(KEY, record.value)      // ← record.value 是 reactive 代理
```

**根因**：`ref(obj).value` 返回 `reactive()` 代理（Proxy）。`kvSet` → `dbPut` 把对象交给
IndexedDB 的结构化克隆算法，而该算法对带 `[[ProxyHandler]]` 的对象直接抛 `DataCloneError`。

**已实测确认**（Node，同一套结构化克隆算法）：

```text
ref(obj).value 检查：
  isProxy   : true
  isReactive: true
structuredClone(record.value)                    -> DataCloneError
structuredClone({ key, value: record.value })     -> DataCloneError   ← kvSet 的实际形状
structuredClone(toRaw(record.value))              -> 克隆成功
structuredClone({ ...record.value })              -> 克隆成功
```

项目自身在 `src/stores/chat.ts:9-10` 的文件头注释里已经写明这条约束
（"写入 IndexedDB 前必须把响应式代理展开成普通对象"），
`src/stores/settings.ts:56` 也用 `JSON.parse(JSON.stringify(...))` 做了脱代理，
**`privacy.ts` 是全项目唯一漏掉的地方**。

**用户可见后果**（因果链）：

1. `setPin` 内部 catch 到 DataCloneError → `errorText` 变成英文
   `Failed to execute 'put' on 'IDBObjectStore': #<Object> could not be cloned.`
   → 页面同时显示"已启用"和这句英文报错。
2. **PIN 从未写入数据库**。但 `record.value` 已在内存里置为 `enabled: true`，
   所以本次会话 UI 显示"已启用"，**刷新后锁默默消失**（安全功能静默失效）。
3. 此时"关闭隐私锁"按钮出现 → `disablePin`（无 try/catch）→ Promise 拒绝
   → `MeView.vue:111` 的 `pinBusy.value = false` 永远执行不到，按钮永久卡在 busy。

**修复**：`await kvSet(KEY, { ...record.value })`（或 `toRaw(record.value)`）。
建议同时在 `dbPut` 层对 `DataCloneError` 兜底成中文提示。

### BUG-2 [严重·手机端] PIN 在局域网 HTTP 下必然抛错

**位置**：`src/utils/pin.ts:11`

```ts
const digest = await crypto.subtle.digest('SHA-256', data)
```

**根因**：`crypto.subtle` **只在安全上下文（HTTPS / localhost）存在**。
非安全上下文里它是 `undefined`。

**为什么必然命中**：项目自己的真机调试流程就是局域网 HTTP ——
`vite.config.ts:12-16` 设了 `host: true` 并注释"方便手机连同一局域网真机调试"，
手机访问的是 `http://192.168.x.x:5173`。

**后果**：`hashPin` 抛 `TypeError: Cannot read properties of undefined (reading 'digest')`，
被 `setPin` 捕获后原样显示在页面上。与 BUG-1 叠加 → **PIN 功能在任何场景都无法使用**。

**修复**：入口守卫并给出可读提示，例如

```ts
if (!globalThis.crypto?.subtle) {
  throw new Error('当前环境不支持加密摘要：请用 HTTPS 或 localhost 打开')
}
```

### BUG-3 [严重] 问数图表在第一次训练后不显示

**位置**：`src/views/PredictView.vue:76-80`

```ts
watch(result, () => {
  if (result.value && canvas.value) {
    drawForecastChart(canvas.value, ...)
  }
})
```

**根因**：`watch` 默认 `flush: 'pre'`，回调在组件重渲染**之前**执行。
而 `<canvas ref="canvas">` 位于 `<section v-if="result">` 内（:132-135），
第一次训练时 `result` 刚从 `null` 变为对象，DOM 里还没有 canvas
→ `canvas.value === null` → **绘制被静默跳过**。
全组件只有这一处和 `onMounted`（那时 `result` 还是 null）会触发绘制。

**用户可见后果**：问数 → 示例数据 → 训练并预测 → 指标和预测数值都出现，
但**图表区域是空白的**；必须再点一次"训练并预测"图才会出现。

**验证**：两个独立子代理分别用真实 Vue 3.5.42 的自定义 renderer 探针复现：

```text
第 1 次运行: [watch cb] canvasEl = NULL  →  [ref fn] canvas attached
第 2 次运行: [watch cb] canvasEl = mounted
```

**修复**：`watch(result, () => {...}, { flush: 'post' })`。

### BUG-4 [严重] 导出长图在手机上会生成空白图或直接失败

**位置**：`src/utils/exportImage.ts:46`、`:199-206`、`:316-320`

```ts
const MAX_CANVAS_H = 7000   // :46 注释自述"浏览器限制约 16384px"
const totalH = Math.min(height, MAX_CANVAS_H)          // :199  逻辑像素
canvas.width  = Math.round(WIDTH * scale)              // :201  WIDTH=750, scale∈[2,3]
canvas.height = Math.round(totalH * scale)             // :202  ← 上限没乘 scale
```

**根因**：高度上限按**逻辑像素**判断，但画布尺寸是**设备像素**（乘了 scale）。
守门条件因此完全没起到注释声称的作用。

**精确验算**：

```text
dpr=3 (现代 iPhone, scale=3):
  画布 = 2250 × 21000 设备像素 = 47,250,000 像素
  超过 16384 维度上限        : 是（21000 > 16384，正是注释自己写的那个限制）
  超过 iOS 面积上限 16.7M    : 是
  按 iOS 面积限制，可用逻辑高度只有 2485px
  扣除页眉(176)+页脚(116) 后 ≈ 49 行文字

dpr=2: 画布 1500 × 14000 = 21,000,000 像素，同样超过 iOS 面积上限
```

而代码允许到 7000 逻辑像素 ≈ **152 行文字**，`ChatView.vue:159` 更是允许导出最近 60 条消息
（60 条按每条约 3 行算 ≈ 10852 逻辑像素）。**49 行到 152 行这一整段必然失败**。

**后果**：`toBlob` 返回 null → 抛"图片生成失败"，或得到一张空白图；
用户只看到"导出失败"一句，无法自查。附带内存：单张画布
2250×21000×4B ≈ 189MB，叠加分享兜底的二次绘制可达 ~380MB，移动端极易被 OOM 杀掉。

**修复**：把上限换算到设备像素后再判断，例如

```ts
const maxDeviceH = Math.min(16384, Math.floor(16777216 / (WIDTH * scale)))
const cap = Math.floor(maxDeviceH / scale)
```

把 `cap` 传进 `layout()`；或当内容过高时自动把 scale 降到 2 / 1。

### BUG-5 [中] 流式传输中途断开 → 逃逸成原始英文 TypeError，且不重试

**位置**：`src/api/llm.ts:189-207`

`for await (const data of parseSSEStream(res.body))` 只 catch 了 `JSON.parse`，
没有包住 `reader.read()`。已收到 HTTP 200 响应头后连接被切断（Wi-Fi/蜂窝切换、
进隧道、反代掐断）时，`read()` 以 `TypeError: network error` 拒绝。

**后果**：
1. 该 error 既不是超时也不是 `ApiError` → `isRetryable`(:45-55) 落到 `return false`
   → **一个 token 都没吐出来也不重试**，而这恰恰是最该重试的时机。
2. 违反模块注释自己声明的契约"所有失败都抛出 ApiError（用户主动取消除外）"，
   `chat.ts:311` 把英文 `network error` 直接展示给用户。

**修复**：for-await 外层包 catch，`isAbort/isTimeout` 原样透传，
其余包成 `new ApiError('流式传输中断：…', 0)`（status 0 ⇒ 可重试）。

### BUG-9 [中] 90 秒超时是"总时长"而非"空闲"，且超时会被重试

**位置**：`src/api/llm.ts:16-17`、`:83-85`、`:231`、`:243-246`

计时器在第一次 fetch 之前上膛，**每收到一个 delta 都不重置**
（`markEmitted`(:202-204) 只置标志位）。

**后果 A（长回答被腰斩）**：模型连续吐字超过 90 秒（长文总结、推理模型很常见）时，
流被中止、回答在句子中间切断；因 `emitted === true` 不重试，
最终抛"请求超时（超过 90 秒未完成）"。用户看着字正常在出却突然报超时。
同时 `chat.ts:331-334` 仍把半截回答当正常消息入库，`:346-357` 还拿它抽取记忆。

**后果 B（等待时长与文案不符）**：首 token 超过 90 秒时 `emitted === false`
→ 超时可重试（`isRetryable:46`）→ 默认 `retries = 2`，最坏等待
≈ 90×3 + 0.8 + 1.6 ≈ **274 秒**，但报错文案仍写"超过 90 秒未完成"。

**修复**：(a) 改为空闲超时（每次 `onDelta` 里 clearTimeout + 重新上膛）；
(b) 从 `isRetryable` 去掉 timeout，或把文案改成"共等待 N 秒仍未完成"。

### BUG-10 [中] IndexedDB 打开失败的 Promise 被永久缓存 → 数据层再也起不来

**位置**：`src/db/index.ts:33-38`、`:80-91`

```ts
let dbPromise: Promise<IDBDatabase> | null = null
function openDatabase() { if (dbPromise) return dbPromise   // 只判空，不判是否已 rejected
```

**触发**：任一打开失败路径命中一次即可 ——
(a) 另一个标签页以旧版本持有 DB → `onblocked`（**版本升级部署后必现**）；
(b) 浏览器阻止站点存储 / 沙箱 iframe → SecurityError。

**后果**：`dbPromise` 永久是一个已 rejected 的 Promise（全文件唯一的
`dbPromise = null` 在 `:85` 的 `onversionchange` 里，覆盖不到这条路径），
此后**每一次** DB 调用都立刻拿到同一个拒绝值。用户按提示关掉其它标签页后重试也没用。
更糟的是被挡住的 open 请求在占用方关闭后其实会继续完成并 `onsuccess`，
但 `resolve` 早已失效，**这个连接无人持有也永不 close**。
整页刷新前数据层完全不可用（会话列表空、消息不落库只 console.warn、历史拉不到）。

**修复**：所有 reject 路径顺手 `dbPromise = null`，并加
`dbPromise.catch(() => { dbPromise = null })` 兜底。

### BUG-11 [中] 问数参数输入框未校验未夹紧 → 原始 tfjs 报错 / 静默空预测

**位置**：`src/views/PredictView.vue:117-119`

```html
<label>窗口 <input v-model.number="config.window" type="number" min="2" max="12" /></label>
```

`min`/`max` 不会被强制（没有表单提交），而 `v-model.number` 在输入框被清空时
给的是**空字符串**（Vue 的 `looseToNumber` 在 `parseFloat` 为 NaN 时返回原值）。

**已实测复现**：

```text
window 为空串时：
  解构默认值 window=4 生效? 否 —— 默认值只对 undefined 生效
  series.length < window+3 -> 7 < "3" = false      ← 字符串 "3" 被强制转换，守卫被绕过
  buildWindows 循环次数 = 7
  series.slice(0 - window, 0) = []                 ← 每条窗口都是空数组
  => 喂给 tensor2d 形状非法

horizon 为空串时：
  rollForecast 循环次数 = 0 => 预测步数 0，静默返回空数组，无任何报错
```

**后果**：清空"窗口"后点训练 → 红色错误条显示原始英文
`Tensor must have a shape comprised of positive integers but got shape [7,].`；
清空"预测" → 结果卡显示"预测步数 0"和空的预测列表，**完全没有任何报错**。

**修复**：在 `run()` 里统一清洗：

```ts
const clamp = (v: unknown, lo: number, hi: number, d: number) => {
  const n = Number(v)
  return Number.isFinite(n) ? Math.min(Math.max(Math.trunc(n), lo), hi) : d
}
```

## 五、已确认「干净」的部分

为避免误判，以下高风险点已逐条核对，**未发现问题**：

- **IndexedDB 事务生命周期**：全库无"建事务 → await 别的 → 再用事务"的写法，
  不存在 `TransactionInactiveError` 风险。
- **游标分页 `dbGetPageByIndex`**：先判 `!cursor || rows.length >= limit` 再 push、
  读满即 resolve，无越界、无死循环、无跳漏。我用 45 条 / 100 条两种会话规模手工验算
  了"加载更早历史"的全过程，**没有 off-by-one，不会漏消息**。
- **复合索引区间**：`IDBKeyRange.bound([sessionId, 0], [sessionId, MAX_SAFE_INTEGER])`
  对 `['sessionId','createdAt']` 索引正确且单会话封闭；`'prev'` + `reverse()`
  取"最近一页"正确；`loadOlderMessages` 的闭区间上界 + 按 id 去重也正确。
- **索引完整性**：代码用到的 5 个索引名全部在 `onupgradeneeded` 里建过，
  不存在"用了没建的索引"；v1→v2 升级路径幂等。
- **SSE 解析器主体**：多行 `data:` 用 `\n` 连接正确；`\n\n` 事件边界推进正确；
  无空行结尾的尾事件冲刷正确；`TextDecoder` + `{stream:true}` 的跨 chunk 多字节处理
  **正确**（字节级切分验证中文不被破坏）。
- **重试/取消语义**：`isAbort`/`isTimeout`/`isRetryable` 条件没有写反；
  `emitted` 保证"已吐字绝不重试"；用户取消不会被当成可重试也不会弹错误条。
- **定时器与监听器泄漏**：`linkSignals` 与 `delay` 的定时器/监听在
  resolve、abort、dispose 三条路径上都清理，每次重试新建并 finally dispose，无累积。
- **Markdown 分块缓存**：缓存以**块源码文本**为 key、memo 以**整篇源码**为 key，
  不存在"按 index 索引导致陈旧 HTML"的问题；`lastSource`/`lastBlocks` 同帧成对写入，
  streaming 时末块绕过缓存 —— 多实例、同源/异源、streaming 切换等场景均返回正确 HTML。
- **XSS**：所有分支的 HTML 都经 DOMPurify 默认配置消毒，
  `ADD_ATTR: ['target','rel']` 不构成漏洞，`javascript:` 链接会被拦掉。**不可达。**
- **`id.ts` 的降级**：`crypto.randomUUID` 不可用时有 `Math.random` 兜底，正确。

### 10.2 关键取舍

- **展示层合并（可逆）**：14 个分类 chip 在手机上要横着翻好几屏，没人找得到人，所以加了「组」这一层，chip 从 14 降到 7。
  数据一条不用改；以后再想拆开或重新归并，只改 `CATEGORY_GROUPS` 一张表，而不是去动 80 多位角色的 `category` 字段。
- **折叠动画不依赖内容高度**：用 `grid-template-rows: 0fr → 1fr` 实现，因此**无需预知内容高度**；
  用 `visibility` 让收起的内容**脱离 Tab 焦点顺序**；`--dur` 在 `prefers-reduced-motion` 下被压成 1ms，动画自动退化。
- **DataCloneError 防护**：`stores/personas.ts` 写库前**逐字段展平成普通对象**（响应式 Proxy 无法被结构化克隆 ——

### 11.2 关键取舍

- **虚拟滚动为什么要求定高**：定高才能用「`scrollTop` ÷ 行高」直接算出可见区间，不必测量每一行。
  代价是长文本必须截断（分块行用两行截断 + 省略号），要看全文就得另开一层 ——
  这是**有意的功能折损**，换的是滚动时的稳定与流畅。88px / 36px 都是「脚本常量 + CSS 注释」
  两处交叉标注的硬约束，**改一处就必须改另一处**。
- **刻意不用 `margin`、不用 `border` 画分隔线**：`margin` 不计入元素 `height`，
  会把实际行距撑得比虚拟滚动假设的 88px 大，**越滚越偏**；`border` 会参与盒子尺寸、
  破坏 36px 这个基准，所以 CSV 的分隔线用 `box-shadow: inset` 画。
- **用 padTop / padBottom 占位而不是绝对定位**：绝对定位对 `<table>` 不成立（会破坏表格布局），
  而本项目两处用它的地方一个是分块列表、一个是 CSV 预览表格 ——
  用上下两个占位把滚动高度撑起来，两种情况都能用。
- **分块面板自己就是滚动容器**：虚拟滚动读的是该容器的 `scrollTop`，
  若让整页承担滚动，读到的位置与可见行就对不上了。
- **单问约束为什么不能只数问号**：「是 A 还是 B」整句**只有一个问号**，
  按问号计数一定漏判。所以除问号计数外还有「还是 / 或是」、开放式疑问词
  （什么 / 为什么 / 怎么 / 哪些）、要求描述或列举等多条规则。
  重复检测也做成两级：归一化（去空白、去标点、去语气词）比较完全相同直接判重，
  否则再过一次 Dice 二元组相似度（阈值 0.82）与长问题包含判定 ——
  模型换个说法重问时字面不同，但相似度仍然很高。
- **为什么聊天列表不改虚拟滚动**：这条要在报告里说清楚 —— `useVirtualList` 是**定高**的，
  而聊天消息高度可变；变高虚拟滚动需要逐行测量并在滚动中反复校正，
  还会与「贴底跟随」和「下拉刷新加载更早历史」相互冲突，做不好就是消息跳动或错位。
  因此长会话**有意保留** IndexedDB 游标分页（`PAGE_SIZE = 30`）+ 提示词历史 20 条，
  9.1 中这一行**仍然标 `⚠️ 方案不同`**，本批**没有**改。
- **CSV 与粘贴共用一条链路**：选列后写回的是**同一个 textarea**，
  后续走 `textarea → parseSeries → points → trainForecast`，不存在第二套解析。
  好处是导入后用户还能在数据框里继续手改，两条入口的行为完全一致。
- **解析畸形输入不抛异常**：引号内的逗号 / 换行 / `""` 转义按字面量处理、兼容 CRLF 与 LF、剥掉 BOM、
  表头只在「首行有非空且非数字单元格」时识别；行列不齐一律补齐或截断。
  这是用户随手从 Excel / 问卷导出的文件，**把能看的部分显示出来比报错更有用**。

## 十二、指标口径修复与跨会话搜索复核记录

本轮起因是一次**功能缺口盘点**：逐条核对需求文档的 26 条 FR 时，发现两处问题 ——
一处是**需求要求了但没做**（FR-D1 的「训练/测试切分」），
一处是**做了但没做对**（评估指标算在训练集内，却没有任何说明）。
后者比前者严重：缺功能只是少一项，而指标口径错误会让人**高估模型质量**。

### 12.1 交付内容

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 训练/测试切分 | `src/ml/train.ts` 的 `splitSeries()` | 按**时间顺序**切分，测试集取最后一段（默认占 20%）；纯函数 + 4 个边界测试（短序列、比例越界、非法比例、单点序列） |
| 指标改为测试集 | `train.ts` 的 `computeMetrics` 调用点 | `metrics` = **测试集窗口**（训练时从未见过其标签）；另存 `trainMetrics` = 训练集内拟合，用于对照过拟合落差 |
| **消除数据泄漏** | `train.ts` 的 `minMaxScale(series.slice(0, splitIndex))` | 归一化的 min/max **只用训练段**估算；若把测试段算进来，缩放器就"见过"测试数据，指标虚高。整条序列仍用这组 min/max 缩放，所以测试段取值可能落在 `[0,1]` 之外 —— 这是它应有的样子 |
| 界面标明口径 | `PredictView.vue` | 指标卡正上方新增「测试集指标 · 这 N 个窗口未参与训练」；下方给出「前 X 点训练 / 后 Y 点测试」与训练集内 R² 作对照，落差 > 0.1 时提示「可能过拟合」 |
| 跨会话搜索 | `src/utils/search.ts`（新增）、`src/db/index.ts` 的 `dbScanByIndex`（新增）、`stores/chat.ts`、`ChatView.vue` | 按会话标题与消息正文搜索；命中词高亮、显示所属会话与时间、点击跳转；结果走定高虚拟滚动 |

### 12.2 关键取舍

- **为什么必须按时间切分**：时间序列**不能打乱**。随机切分等于拿「未来」评估「过去」，指标会虚高得毫无意义；
  只有按时间留出最后一段，测试集才是真正的样本外。
- **为什么缩放器只能用训练段拟合**：缩放本身也是模型的一部分。用全体数据估 min/max，
  信息就从测试集泄漏进了训练流程 —— 这是最容易被忽略、又最常出现在学生项目里的错误。
- **为什么搜索要「扫描/命中双上限 + 扫描前刹车」**：消息表没有全文索引，只有 `[sessionId, createdAt]` 复合索引。
  不能 `getAll` 全表读进内存（手机内存吃紧且会明显卡顿），所以用游标逐条交给回调，
  命中满或扫满就立刻让游标停下 —— 而不是读完再截断结果。
- **为什么搜索不做分词/模糊/拼音**：本轮目标是「找得到」，连续子串匹配已能覆盖绝大多数场景；
  引入分词会带来词典体积与中英文混排的正确性问题，收益不成比例。

### 12.4 仍然存在的真实局限

1. **本批两项都没有在真实浏览器里点过**：搜索的防抖、虚拟滚动、与下拉刷新共存，
   以及训练指标卡片的新文案，**都只经过类型检查与静态推理**，没有运行时验证、没有截图。
2. **搜索的排序语义有局限**：消息只有 `[sessionId, createdAt]` 复合索引、**没有全局时间索引**，
   游标是升序扫的，所以命中达上限被截断时，拿到的是「索引靠前的部分」而**不是「全局最新的 50 条」**。
   在会话数很多、消息量很大时，用户真正想找的新消息**可能不在结果里**。
   界面会如实显示「只显示了前 N 条 · 已扫描 M 条」，但这不等于结果齐全。
   **改进方向**：按会话的 `updatedAt` 倒序、逐个会话区间扫描，让「新会话优先」。
3. **搜索的 UI 零自动化覆盖**：项目 vitest 跑在 node 环境（无 jsdom），mount 不了 `ChatView`，
   所以只测了 `src/utils/search.ts` 的纯函数；`dbScanByIndex` 也没有单测（无 `fake-indexeddb`，未新增依赖）。
4. **「跳到命中消息」只做到尽力而为**：`selectSession` 只加载最近 30 条，
   命中若在更早历史里，只会提示「这条消息在更早的历史里」，**没有**逐页加载直到找到。
5. **训练指标仍受数据量影响**：切分只解决了口径问题，不代表指标可信 ——
   样本点很少时测试集只有个位数窗口，R² 波动会很大；界面虽然标了窗口数，但不会劝阻用户。
6. **指标卡片的新文案同样未在真机看过**：文案较长，在小屏上是否换行挤压布局未验证。

> 综上：本轮的**修复**（12.1）与**门禁**（12.3）都已完成，
> 但第 1、2、4、6 条意味着「口径已经正确」不等于「这个功能已被证明好用」。
