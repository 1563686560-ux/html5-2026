# AI 智囊团 —— 开发计划

> 移动端 Web 应用 · Vue 3 + Vite + TypeScript
> 配套文档：《需求分析和项目进度安排》（需求基线 v1.6）
> 本文档定义产品定位、阶段划分、阶段详情、前端要求与技术预案。
>
> **状态图例**：✅ 已实现 · ⚠️ 部分实现 · ❌ 未实现（计划中）

---

## 一、产品定位

**一个随身 AI 智囊团**：把「找人聊、查自己的资料、算数据趋势」三类场景合到一个 App 里，用统一记忆层串起来，手机打开即用。

| 能力     | 定位                       | 一句话说明                                                       |
| -------- | -------------------------- | ---------------------------------------------------------------- |
| **问人** | **主打** · 多角色对话平台  | 先贤、产品经理、各科老师、运营、演员……外加万能对话入口与自定义角色 |
| **问知** | 技术担当 · 知识库问答      | 导入自己的资料，基于资料回答并标注出处                           |
| **问数** | 第二引擎 · 数据预测        | 在手机浏览器里本地训练模型并预测                                 |

> 「问人」是产品主体，不是"先贤对话"的附属：**先贤只是 14 个细分分类中的一类**，核心命题是"想找谁聊就找谁聊"。

**双引擎架构**：

- **云端大模型引擎** —— 对话、辩论、Embedding 走 OpenAI 兼容 API
- **本地机器学习引擎** —— 数据预测走 TensorFlow.js，在设备内训练，不依赖网络

两条引擎互为备份：大模型不可用时本地引擎仍可完整演示。

## 三、阶段详情

### P0 共享地基（第 1 周）✅

**交付**：一个能连上任意大模型聊起来的最小 App。

**任务**

- 工程骨架：Vue 3 + Vite + TypeScript、路由（hash 模式、全懒加载）、底部导航、暗色主题
- **大模型客户端层（核心资产）**
  - 对话补全：OpenAI 兼容协议封装，厂商可切换
  - **SSE 流式解析**与增量渲染
  - 空闲超时、退避重试、错误兜底、请求中断（`AbortController`）
  - Embedding 接口封装（与对话接口分开配置 endpoint / key / 模型名）
  - API Key 本地存储，不写死在代码里
- 持久化层：IndexedDB 封装（会话、消息、记忆、文档分块、向量、KV）
- 通用组件：流式打字机渲染、Markdown 渲染、消息气泡、「思考中」状态、空状态、骨架屏、Toast

**前端要求**

- CSS 变量主题体系 + 暗色模式（**实现方式见 §6.1，与"CSS 媒体查询"不同**）
- 移动端基础：安全区 `env(safe-area-inset-*)`、`100dvh`、禁缩放、消除点击高亮
- 基础组件库：按钮 / 输入框 / 卡片 / 空状态 / **骨架屏**
- 底部导航 + 路由切换过渡动画

**技术点**：SSE 增量解析、流式渲染性能、存储抽象

**风险预案**：只接 OpenAI 兼容厂商（DeepSeek / 通义 / 智谱），避免协议差异

---

### P1 智能体（第 2 周）· 保底 ✅

**交付**：跟角色文字对话，流式输出、有上下文、能存档。

**任务**

- 角色库：每人一套**结构化人设 JSON**（性格 / 口癖 / 知识边界 / 立场 / 禁谈话题）
- 提示词组装器：人设 + 记忆 + 历史 → 最终 prompt
- **万能对话入口**：不选角色直接开聊（`assistant` 人设）
- 会话管理：多会话、重命名、删除、导出分享长图
- 首页「能力广场」：能力卡入口

**前端要求**

- 聊天界面交互：自动滚动到底、上滑加载历史、长按复制、下拉刷新
- **流式打字机渲染节流**：用 `requestAnimationFrame` 批量提交更新，而不是每个 token 触发一次 DOM 更新
- **Markdown 增量渲染**：只重绘变化部分，长回答不掉帧
- 会话列表骨架屏 + 空状态

**为什么必须先做**：它是保底。做完这一步，已经有一个能答辩的完整 App。

---

### P2 统一记忆层（第 3 周）· 融合剂 ✅

**交付**：跨模块的「AI 记得你」。

**任务**

- 用户画像本地存储：偏好、正在做的事、聊过的话题
- **记忆抽取**：对话结束后由模型总结出「值得记住的事实」并入库
- **上下文注入**：各模块发起请求时自动带上相关记忆
- 隐私模式开关页：Key 本地存、数据本地存、PIN 锁
- 可选加分：记忆权重与衰减

**前端要求**

- 隐私设置页交互：开关、密码输入、加载态与错误态
- **记忆可视化**：用标签 / 卡片列表把「AI 记住了什么」呈现出来，让抽象概念看得见

**价值**：这是「一个智能体」与「几个工具拼在一起」的分水岭，也是答辩时回答「为什么这算一个产品」的标准答案。

---

### P3 知识库 RAG（第 3~4 周）· 主打，做深 ✅

**交付**：丢一篇论文 / 笔记进去，提问，答案带出处。

**任务**

1. **文档导入**
   - 粘贴文本、`.txt`
   - `pdf.js` 解析 PDF 文本层
   - 必须保留「粘贴文本」入口作为兜底（扫描版 PDF 无文本层）
2. **中文友好分块**
   - 按段落切分 + 重叠窗口，保留块与原文位置的映射关系
3. **Embedding 向量化（走 API）**
   - 调用 OpenAI 兼容的 `/v1/embeddings`
   - 候选模型：通义 `text-embedding-v3`、智谱 `embedding-3`、硅基流动上的 BGE 中文系列
   - 批量请求 + 本地缓存：同一分块只向量化一次，存 IndexedDB
   - 向量以 `Float32Array` 存储，记录维度
4. **向量检索**
   - 纯 JavaScript 计算余弦相似度
   - Top-K 召回 + 相似度阈值过滤，无需引入向量数据库
5. **带出处的回答**
   - 检索片段注入 prompt，要求模型标注引用来源
6. **降级链（本项目特有）**
   - DeepSeek 无 Embedding 接口 → **关键词检索永久兜底**，向量失败自动回落

**前端要求**

- 引用高亮：点击引用定位到原文并高亮
- 文档导入 / 解析 / 向量化的分步进度反馈

**技术点**：分块策略、Embedding、向量相似度检索、RAG 提示词设计、引用定位

**这是前端技术分与技术含量的最大来源，人力应优先压在这里。**

### P4 预测分析台（并行支线，第 2~4 周）· 第二引擎 ✅

**交付**：上传 CSV，在手机浏览器里训练模型并出预测。

**任务**（逐项标注真实状态，避免整节 ✅ 掩盖个别未做项）

- ✅ 数据导入 + 预览 + 缺失值处理 + 归一化（`minMaxScale`）
- ✅ **训练集 / 测试集切分**（本轮补上）：按**时间顺序**切，测试集取最后一段；`splitSeries()` 是纯函数并有 4 个边界测试
- ✅ **TensorFlow.js 本地训练**（16→8→1 全连接），跑在 Web Worker，训练进度可视化
- ✅ 评估指标：RMSE / MAE / MAPE / R² —— **算在测试集（留出集）上**，不是样本内拟合
- ⚠️ 滑动窗口外推预测 ✅ + **导出报告图 ❌ 未实现**（`PredictView.vue` 与 `ml/chart.ts` 里没有任何 `toDataURL` / `download` / 分享能力；会话长图导出是另一套，在 `ChatView`）

**指标口径（答辩会被问，必须能答）**

- 切分顺序：**时间序列不能打乱**，测试集取最后一段；打乱就等于拿未来评估过去
- **归一化只用训练段估算 min/max**：否则缩放器「见过」测试数据，属于**数据泄漏**，指标虚高；
  整条序列仍用这一组 min/max 缩放，所以测试段取值可能落在 `[0,1]` 之外 —— 这才是它应有的样子
- 界面在指标卡正上方标明「测试集指标 · 这 N 个窗口未参与训练」，并给出训练集内 R² 作对照；
  两者差距大于 0.1 时会提示「可能过拟合」
- 图上测试段那条「拟合」线**实际上就是样本外预测**（`fitted` 覆盖全部窗口，但模型只在训练段窗口上训练过）

**修复记录（本轮）**：在此之前，四个指标全部用**训练集自身的拟合值**计算（`train.ts` 当时的注释即写着「训练集内的拟合指标」），
且界面没有说明 —— 看的人会把 R² 理解成模型准确率。现已改为测试集指标并在界面标明口径。

**前端要求**

- 训练进度可视化：Canvas 实时绘制 loss 曲线
- 预测结果折线图（Canvas 2D）
- 训练配置面板的响应式布局

**为什么并行**：技术栈与主线**完全独立**，从第 2 周起即可单独开线。它是全队唯一**不需要网络、不可能翻车**的模块，是断网时的演示保险。

**这是「智能实现在前端」最有力的证据**——模型不用别人的，是在用户手机里训出来的。

### P5 多角色平台扩充（第 5 周）✅

**交付**：**81 位**内置角色、**14 个细分分类**、**7 个展示分组**，「问人」从"先贤对话"变成"角色对话平台"。

**任务**

| 展示分组（角色广场） | 归入的细分分类                           | 人数 | 典型用途                                 |
| -------------------- | ---------------------------------------- | ---- | ---------------------------------------- |
| **万能对话**         | `assistant`                              | 1    | 不挑角色，直接开聊                       |
| **先贤智者**         | `sage`                                   | 8    | 借古人/名家视角聊价值观、人生、科学      |
| **职场与商业**       | `pm` / `operator` / `business` / `law`   | 20   | 怼 PRD、写活动方案、简历面试、合同与财务 |
| **学习与学术**       | `teacher` / `academic`                   | 19   | 讲题答疑、论文选题、文献检索、升学备考   |
| **技术与创意**       | `tech` / `design` / `actor`              | 19   | 写代码、做设计、剪辑配音、练台词         |
| **生活与健康**       | `health` / `life`                        | 14   | 看病前的常识、吃与练、情绪与关系         |
| **我的角色**         | `custom`（+ 一句话临时人设）             | 0+   | 用户自建 + 「想和谁聊」生成的临时人设    |

- **人设模板化**：`category` 从 `'assistant' | 'sage'` 两类扩展为 **14 个细分分类**（`CATEGORIES`），按类别组织人设字段
- **分类合并只发生在展示层**：`CATEGORY_GROUPS` 把 14 个细分分类归成 **7 个展示分组**（chip 从 14 个降到 7 个）；细分分类保留在数据里，合并掉的信息由角色卡上的「细分身份标签」补回
- **角色数据分 4 个文件**：`personas.ts`（类型 + 通用助手 + 8 位先贤 + 分组表 + 工厂函数）、`personas.pro.ts`（19 位：产品经理 / 老师 / 运营 / 演员）、`personas.domains.ts`（31 位：技术 / 设计 / 职场 / 健康 / 法律 / 生活 / 学术）、`personas.more.ts`（22 位：宏观 / 咨询 / 谈判 / 劳动法 / 翻译 / 写作 / 科普 / 文献检索 / 博物馆 / 考公 / 安全 / 游戏 / 插画 / 空间 / 剪辑 / 配音 / 中医 / 口腔 / 情感关系 / 家庭教育 / 园艺 / 烘焙）
- **角色注册表**：新增 `src/stores/personas.ts`，`all = 内置 + 自建 + 临时`，`resolve() / find()` 按 id 解析；自建角色持久化在 IndexedDB 的 `kv`（键 `custom-personas`），写库前逐字段展平成普通对象（防 `DataCloneError`）；读库失败给出 `storageWarning` 而不是静默清空
- **角色广场分组**：7 组**折叠展开**（默认展开前两组），支持关键词搜索、展开全部 / 收起全部；搜索或选中分类时自动全部展开
- **自定义角色**：新增 `src/views/PersonaEditView.vue`（路由 `/personas/edit`），可新建 / 编辑自建角色、把「一句话临时人设」转正；删除为两步确认（先上膛，3 秒未确认自动复位）
- **首页万能对话入口**：不选角色直接开聊；也可一句话描述"想和谁聊"，即时生成临时人设（FR-B2）

**前端要求**

- 角色广场的 7 组折叠展开布局 + 关键词搜索与筛选交互（展开动画用 `grid-template-rows: 0fr → 1fr`，`prefers-reduced-motion` 下退化为瞬时）
- 自定义角色表单的校验与错误提示
- 首页从"四张能力卡"改为"能力卡 + 万能对话入口"

**工作量提示**：这一阶段主要是**内容与组织方式**的扩充，技术风险低，但人设文案量大（14 个细分分类 / 81 位角色）。

**联动改动**：`src/stores/chat.ts` 的当前角色改走注册表解析（否则自建角色会被静默解析成默认助手）；提示词组装器注入「当前日期」的条件由 `category === 'assistant'` 改为 `category !== 'sage'` —— 当代角色都需要真实日期，先贤不能有。

**顺手修的工程问题**：`vite.config.ts` 加 `server.watch.ignored`（编辑器的原子写入临时文件会让 Vite 的 watcher 抛 EBUSY 并**整个 dev server 退出**）；`eslint.config.js` 给 `scripts/**/*.js` 补注入全局变量 `univerAPI / api / doc`（原先漏配导致 12 个 no-undef）；`AppIcon` 新增 `search` 与 `chevron` 图标。

**未验证**：折叠动效与搜索手感的真机点验尚未完成，留待 P6 真机联调时人工确认。

### P6 集成与体验收口（第 5~6 周）⚠️ 部分实现

**交付**：真机可跑（浏览器 + `.apk` 安装）、离线可用、可添加到主屏幕。

**任务**

| 项                     | 状态        | 说明                                                       |
| ---------------------- | ----------- | ---------------------------------------------------------- |
| 真机联调与移动端适配   | ⚠️ 待真机   | 安全区、`100dvh`、滚动、下拉刷新、横竖屏限宽、软键盘避让、系统字号缩放均已实现；仍需真机确认 |
| PWA（Manifest + SW）   | ✅          | 离线壳缓存 + 三档图标（脚本生成），跨域请求不进缓存        |
| **Capacitor 打包 `.apk`** | ❌ 未实现 | 未安装 `@capacitor/*`、无 `capacitor.config.ts`、无 `android/` |
| 性能优化               | ✅          | rAF 节流、Markdown 增量渲染、路由懒加载、pdfjs 改动态引入（分包 467.5 KB → 5.4 KB） |

**Capacitor 说明**：用 Capacitor 把同一套前端代码包装成 Android 应用（`.apk`）安装到真机，装好后离线打开、离线训练的体验与浏览器内一致。iOS 打包需 Mac 与开发者签名，本次只保浏览器可用。

**Capacitor 技术要点**

- `pnpm add @capacitor/core @capacitor/cli @capacitor/android` → `npx cap init` → `npx cap add android`
- 构建流程：`pnpm build` → `npx cap sync` → `npx cap open android`（Gradle 出包）
- **注意 hash 路由**：项目用 `createWebHashHistory`，Capacitor 的 `WebView` 加载本地 `file://` 时天然友好，无需额外重写规则
- **注意 Service Worker**：Capacitor 的 WebView 对 SW 支持有限，离线壳在 App 内可能不生效；App 内资源本就打包在本地，影响可控
- **注意相对路径**：`vite.config.ts` 的 `base` 需改成 `'./'`，否则 App 内资源 404
- **注意 API Key 与网络**：App 内跨域策略比浏览器宽松，但仍需 `android:usesCleartextTraffic` 之类配置才能访问自建 HTTP 端点

### P8 猜心（选做玩法，第 6 周）✅

**交付**：用户心里想好一个东西不说，App 每轮只问一个封闭式问题，二十轮内猜出来。

**玩法**：整个玩法由多轮对话驱动，**直接复用「问人」的流式对话与提示词组装**，属于在已有能力上加的一层玩法，不新增技术栈。

**任务**

- **开局与规则**：一句话讲清玩法并提示"心里想好一个东西，先别告诉我"
- **单问约束**：每轮只输出一个问题且必须封闭式（能拿是 / 否回答）；不得一次问多件事、不得重复提问
- **逐步收敛**：每轮根据用户回答更新候选集与置信度，按"先大类后细节"逐层二分缩小范围
- **猜出与结算**：置信度够高或达到最大轮数（如 20 轮）给出答案；显示"第几轮猜中"，猜错可继续
- **对局记录**：轮数、用时、猜中 / 未猜中结果存本地，支持"再来一局"与历史对局回看

**实现要点**

- 走问人的同一套流式通道，但每轮要求模型返回**结构化 JSON**（`{ question, guess, confidence }`）
- 解析失败、一次问了多件事或重复提问时**按规则重问一次**
- 对局内容**不写入记忆层**，避免用户心里想的答案被当成长期记忆留下来

**前端要求**

- 对局界面：问题卡逐轮入场动画、进度指示（第 N 轮 / 最多 20 轮）
- 结算界面：猜中的揭晓动效、历史对局列表

**风险**：结构化输出的稳定性依赖模型，需要"解析失败重问 + 兜底模板"双保险。（**P8 已于本轮完成**：解析失败或违反单问约束只重问一次，第二次仍违规就换用兜底问题继续，对局不会卡住）

**实现记录（本轮完成，P8 不再是待办）**

- `src/prompt/guess.ts`（纯函数，**51 个测试**）：提示词组装、稳健 JSON 抽取（`{ question, guess, confidence }`，容忍代码围栏与前后缀噪声）、单问约束校验、重复检测；`MAX_ROUNDS = 20`、`GUESS_CONFIDENCE_THRESHOLD = 0.8`
- `src/stores/guess.ts`：对局状态机（轮数、问答历史、用时、中断、结算）；对局记录持久化到 kv 键 `guess-history`（最多 20 局），读写失败给 `storageWarning` 而不是静默失败
- `src/views/GuessView.vue`：开局屏 / 对局屏 / 结算屏 / 历史回看四屏
- 路由新增 `/guess`；首页能力区新增「猜心」卡片（subtitle 标「选做玩法」）
- **关键实现**：走 `streamChat` 同一套流式通道（`temperature 0.4`、rAF 批量提交），不新增技术栈；`confidence ≥ 0.8` 且模型确实给出了 guess 才结算；**不写入记忆层**、不污染 `chat.sessions`
- **单问约束的实现细节**：不能只数问号 ——「是 A 还是 B」整句只有一个问号，数问号根本抓不到，所以另配了「还是 / 或是」句式、开放式疑问词（什么 / 为什么 / 怎么 / 哪些）、要求对方描述列举（说说 / 描述 / 列举）等多条规则；重复检测走**两级判断**：归一化比较（去空白、标点、语气词）+ Dice 二元组相似度 `0.82`，再加一条「长问题包含判定」（≥5 字的核心短语被原样搬来也算重复）

**未验证（本轮如实记录）**：环境无 API Key、无浏览器自动化（也没有 jsdom / playwright，且不允许新增依赖），因此
**猜心没有跑过真实模型对话** —— 模型是否真的遵守单问约束，只靠提示词与重问机制保证；
`src/stores/guess.ts` 与 `src/views/GuessView.vue` **没有自动化测试**，自动化测试只覆盖了 `src/prompt/guess.ts` 的纯函数。

**关于「跟随系统暗色」的准确表述**（答辩时注意）：

> 暗色模式**不是**用 CSS `@media (prefers-color-scheme)` 实现的，而是 `src/composables/useTheme.ts` 里用 `window.matchMedia('(prefers-color-scheme: light)')` 读取系统偏好作为默认值，再由 `theme.css` 的 `[data-theme]` 属性选择器切换变量，CSS 侧用 `color-scheme` 声明控件配色。
>
> **这样做的理由**：支持用户在设置页手动覆盖系统偏好（切换后写 `localStorage` 持久化），纯 CSS 媒体查询做不到手动覆盖。

### 6.3 前端性能工程

| 问题                | 手段                                                           | 状态 |
| ------------------- | -------------------------------------------------------------- | ---- |
| 流式输出掉帧        | `requestAnimationFrame` 批量提交（`utils/frameBatcher.ts`），而非每个 token 一次 DOM 更新 | ✅ |
| Markdown 全量重渲染 | 增量渲染 + 分片解析，只重解析变化的末块，块级缓存以源码文本为 key | ✅ |
| 首屏体积            | 路由懒加载（10 个视图全部 `import()`）、构建分包                 | ✅ |
| 主线程阻塞          | PDF 解析与模型训练放 **Web Worker**；Worker 不可用时回落主线程   | ✅ |
| **长会话列表**      | **未用虚拟列表**。实际方案：IndexedDB 游标分页（`PAGE_SIZE = 30`）+ 上滑加载更早历史 + 提示词历史只取最近 20 条 | ⚠️ 方案不同 |
| **大文档分块列表**  | 「分块浏览面板」（本轮新建，此前**没有**分块列表 UI）：点资料卡打开，列出该资料的全部切分块，走自研定高虚拟滚动（`useVirtualList`，行高 88px 与 CSS 严格一致） | ✅ |
| **CSV 预览表格**    | CSV 文件导入 + 预览表格 + 自研虚拟滚动（`useVirtualList`，行高 36px、容器 252px）；同时补齐需求文档 FR-D1 的「CSV / 粘贴 + 预览」 | ✅ |
| pdfjs 首屏体积      | 改为动态 `import('@/rag/pdf')`：`LibraryView` 分包 **467.5 KB → 5.4 KB**，pdfjs 独立成 `pdf-*.js`，只在真正选中 PDF 时才下载 | ✅ |

> **答辩时的正确说法**：这里要**分两件事**讲清楚，既不要笼统说"做了虚拟列表"，也不要再说"没做虚拟滚动"。
>
> - **① 聊天消息列表仍用游标分页**（`PAGE_SIZE = 30` + 上滑加载更早历史 + 提示词只取最近 20 条），这是**有意保留的取舍**：聊天消息高度可变，变高虚拟滚动要逐行测量，还会与贴底跟随、下拉刷新相互冲突，所以选择"在数据库层分页控制内存与请求量，而不是在视图层做虚拟滚动"。
> - **② 分块浏览面板与 CSV 预览表格确实用了虚拟滚动**，而且是自研的 `useVirtualList`（定高：用 `scrollTop ÷ 行高` 直接算可见区间，纯函数 `computeVirtualWindow` + 9 个边界测试），只渲染视口内（外加少量 overscan）的行。
>
> 一个讲取舍、一个讲实现，两处都不必回避。

### 9.3 关键实现细节

- **P3 降级档**：DeepSeek 无 Embedding 接口，故「关键词检索」为永久可用兜底；配置第二家 Embedding 后自动切换到向量检索（阈值 0.25），失败再回落。
- **P3 PDF**：`src/rag/pdf.ts` 用 pdf.js 抽取文本层（`workerPort` 方式加载），扫描版无文本层时提示粘贴兜底。
- **P4 双引擎**：模型 16→8→1 全连接，`min-max` 归一化 + 滑动窗口，纯设备内训练，断网可演示。
- **P4 Worker**：训练默认跑在 Web Worker（`src/ml/forecast.worker.ts`），不阻塞主线程；Worker 不可用时动态加载主线程核心兜底，避免正常路径加载两份 tfjs。
- **P4 指标**：`src/ml/metrics.ts` 提供 RMSE / MAE / MAPE / R²，纯函数可单测。
- **测试隔离**：`parseSeries`/`sampleSeries` 拆到 `src/ml/series.ts`，与 tfjs 解耦，Node 环境可测；训练核心 `trainForecastCore` 在 Node 环境跑通烟雾测试。
- **虚拟滚动（自研）**：`src/composables/useVirtualList.ts` 是**定高**虚拟滚动，纯函数 `computeVirtualWindow` + 9 个边界测试。三个容易踩的点都写进了注释：① 行高必须与 CSS 严格一致（分块行 88px、CSV 行 36px，两处都做了「脚本常量 ↔ CSS」的交叉标注）；② **刻意不用 `margin`** —— margin 不计入 `height`，会把行距撑大，于是越往后滚偏差越大；③ 用 `padTop` / `padBottom` 占位而**不绝对定位**，因为 CSV 预览是 `<table>`，绝对定位会破坏表格布局。另外 `scroller` 用 `watch(..., { flush: 'post' })` 跟踪，面板是条件渲染时也能量到高度。
- **分块浏览面板**：`LibraryView.vue` 点资料卡打开，列出该资料的全部切分块（此前**没有**分块列表 UI）；面板**自身**就是滚动容器（挂在整页滚动上就得反算 `scrollTop` 相对谁）；**单块全文另起一层**盖在列表之上 —— 虚拟滚动要求行高固定，把某一行撑高会让后面所有行错位。
- **CSV 导入与预览**：`src/ml/csv.ts` 是逐字符状态机解析（23 个测试）：引号字段内的逗号 / 换行 / `""` 转义都按字面量处理，兼容 CRLF 与 LF、剥掉 BOM、表头识别（首行含非空且非数字的单元格才算表头，整行数字视为数据）、行列不齐自动补齐，**绝不抛异常**。预览表格 36px 行高（与 CSS 交叉标注）、容器 252px（= 7 × 36）自身滚动、表头 `position: sticky`、分隔线用 `box-shadow: inset` 而不是 `border`（`border` 会参与行高、破坏 36px 基准）。选中列后把该列**写回同一个 `textarea`**，于是 CSV 与粘贴共用 `textarea → parseSeries → points → trainForecast` 一条链路，没有第二套解析，粘贴流程零改动。
- **滑动切换会话**：`src/composables/useSwipeNav.ts`（纯函数 `resolveSwipe` + 8 个测试），判定很严：横向位移 ≥56px **且** 横向至少是纵向的 1.8 倍才算滑动 —— 它与下拉刷新、纵向滚动共用同一片触摸区域；切到头提示「已经是最新 / 最后一条」而不是循环。多指触摸不参与判定。
- **猜心（P8）**：`src/prompt/guess.ts` 的纯函数（组装 / 抽取 / 单问约束 / 重复检测，51 个测试）+ `src/stores/guess.ts` 状态机 + `src/views/GuessView.vue` 四屏；规则细节见第三节 P8。
